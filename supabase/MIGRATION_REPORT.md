## What happened in two passes

**Pass 1 (prior session):** applied `01_schema.sql`/`02_functions.sql`/`03_seed.sql` (core + CRM + HR + accounting + chat/email — 59 tables) and migrated data for the 56 tables that had a matching target. 47 tables were skipped as "no target table" — these were the entire Safety domain (fire/gas/electrical/boiler/structural safety, DSA, consultant engagement, safety audits/RFQ/training/grievances/incidents/documents, water/waste management), which the original schema kit never modeled.

**Pass 2 (this session):** introspected SQL Server metadata (columns, types, defaults, PK/FK, unique constraints, indexes, triggers, views) for all 47 remaining tables directly via `sys.columns`/`sys.foreign_keys`/`sys.check_constraints`/`sys.triggers`/`sys.views`, generated `04_safety_schema.sql` to match, applied it, and re-ran the full data migration.

## Bug fixed in `scripts/migrate-sqlserver-to-supabase.js`

The original script truncated and inserted one table at a time in alphabetical order. Because `Tenants` sorts after most FK-dependent tables (e.g. `Certifications`), and because the script truncated each target table with `CASCADE` immediately before loading it, this was silently dangerous: by the time the loop reached `Tenants`, truncating it with `CASCADE` would have wiped every already-loaded table that references `tenant_id`. It surfaced first as an FK violation (`Certifications` insert failed because `Tenants` was still empty), which is what exposed the ordering problem before any silent data loss occurred.

**Fix:** the script now builds the full table plan first, truncates all target tables together in a single statement (safe since nothing has data yet), sets `session_replication_role = 'replica'` for the duration of the load (bypassing FK/trigger checks so insert order doesn't matter), then restores it and fixes identity sequences at the end.

## Schema conventions used for the new Safety-domain tables (`04_safety_schema.sql`)

Matched the style already established in `01_schema.sql`:
- snake_case table/column names (table-name collisions checked — none)
- `integer generated by default as identity primary key` for all PKs (all 47 tables have a single-column PK; none are composite)
- SQL Server `datetime`/`datetime2` → `timestamptz`; `date` → `date`; all string types (`varchar`/`nvarchar`/`char`) → `text`; `decimal`/`numeric` → `numeric(p,s)`; `bit` → `boolean`
- Defaults translated: `getdate()` → `now()`, bit literals → `true`/`false`, string/numeric literals unwrapped from SQL Server's parens
- 3 unique constraints preserved: `safety_checklist_headings(tab_id, heading_slug)`, `safety_units(tenant_id, name)`, `water_buying(invoice_number)`
- 13 non-unique indexes preserved (mostly on date/category/department columns in the water/waste tables, plus `tab_id` lookups on the checklist tables)

**No FK constraints, check constraints, triggers, or views were added** to any of the 47 Safety-domain tables, because none existed in SQL Server for them — confirmed by direct query against `sys.foreign_keys`, `sys.check_constraints`, `sys.triggers`, and `sys.views` before writing the schema. This isn't a gap introduced by the migration; it reflects how the source app was actually built (these tables carry a loose `FactoryId`/`TenantId`-style scoping column in some cases, unenforced).

## Verification performed

1. **Row counts** — every one of the 103 matched tables compared source vs. target; all exact matches (e.g. `visitor_logs`: 19,658/19,658, `safety_audit_item`: 517/517).
2. **Referential integrity** — queried `pg_constraint` for every FK constraint actually declared in the Supabase `public` schema (24, all pre-existing core-schema ones — `certifications→tenants`, `company_users→tenants/users`, `role_permissions→roles/permissions`, etc.) and checked each for orphaned rows. Zero violations. This mattered specifically because the bulk load ran with FK checks disabled (`session_replication_role='replica'`), so Postgres would not have caught orphans on its own — this was a targeted post-load check, not reliance on constraint enforcement during load.
3. **Identity sequences** — spot-checked that `pg_get_serial_sequence` current values are ≥ `max(id)` on both populated and empty tables (e.g. `safety_audit_item` sequence at 753 with 517 rows — gaps are expected from source-side deletes, the important thing is no future collision).

## Known gaps / things not attempted

- **No dedup or transform of data** — this was a straight structural copy, column-matched by normalized name.
- **No triggers/computed columns added on the Postgres side** — SQL Server had none to port, but if the app currently relies on any application-level logic to backfill `UpdatedAt` etc., that logic still lives only in `web-server.js` today (SQL Server path).
- **`safety_checklist_headings`/`safety_checklist_items` and most `Safety*` tables (e.g. `safety_boiler_safety`, `safety_fire_safety`, etc.) store a generic `form_data` text blob** rather than exploded columns — that's how they exist in SQL Server (dynamic-form pattern), preserved as-is rather than normalized.
- **App code cutover not started** — `src/web-server.js` (5,354 lines, ~730 `.input()`/227 `pool.request()` call sites) plus `src/index.js`, `safety-agent-api.js`, `safety-api.js`, `seed-sample.js`, and two `setup-*-tables.js` files still talk to SQL Server exclusively. Data now exists in both places; only SQL Server is actually read/written by the running app (aside from the already-flagged, still-disabled `ENABLE_SUPABASE_AUTH` auth path).

## Suggested next step

Whenever you're ready to move the app itself, the existing `ENABLE_SUPABASE_AUTH` flag in `src/web-server.js` is a working template for an incremental, feature-by-feature cutover (auth is already fully ported behind it). The natural next slice would be one bounded feature area (e.g. CRM or the Safety inspection forms) rather than the full file at once, given the size.
